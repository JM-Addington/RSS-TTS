# Article Processing Pipeline Overview

This document provides a comprehensive overview of the article processing pipeline, from initial submission to the generation of an RSS feed item.

## 1. Article Submission

Articles can be introduced into the system in two primary ways:

*   **Manual Submission**:
    *   Users can directly paste the text content of an article.
    *   Alternatively, users can provide a URL, and the system will attempt to fetch and extract the main textual content.
*   **Automated Submission via Followed Feeds**:
    *   Users can subscribe to external RSS feeds.
    *   The system periodically fetches new articles from these followed feeds and automatically submits them for processing.

## 2. Article Processing Task (`process_article` in `tasks.py`)

Once an article is submitted, its processing is handled by the `process_article` Celery task. This background task performs several steps:

1.  **Initial Status**:
    *   The `Article` object's status is immediately set to `PROCESSING`.

2.  **URL Content Extraction**:
    *   If the article was submitted via a URL (`article.source_url` is present) and its `text_content` is empty, the system attempts to download and extract the main textual content from the provided URL.
    *   If extraction fails, the article status is set to `FAILED`.

3.  **Title Generation**:
    *   If the `article.title` is empty (e.g., for pasted text or if the source URL didn't provide a clear title), the system uses an LLM (via OpenAI API) to generate a concise title based on the article's content.

4.  **Content Analysis (`ContentAnalysisService`)**:
    *   The `ContentAnalysisService` is invoked to analyze the `article.text_content`. This service is crucial for preparing the content for TTS.
    *   **Summary Generation (New)**: A key output of this service is a concise 2-3 sentence summary of the article content. This summary is generated by an LLM.
    *   **Voice Segmentation and Parameterization**: The service also determines how the article should be narrated. This includes:
        *   Identifying segments of text that might benefit from different voices (e.g., narrator vs. quoted speakers).
        *   Defining voice characteristics for each segment (e.g., tone, TTS model like 'alloy', 'onyx', and speaking speed).
    *   The generated **summary** is saved to the `article.summary` field of the `Article` model.
    *   The detailed voice and segmentation data is stored as a JSON object in the `article.multi_voice_data` field.

5.  **Text-to-Speech (TTS) Generation**:
    *   The system prepares the text for TTS:
        *   If `multi_voice_data` is available and valid, the text is processed according to the defined audio segments and voice parameters. Each segment might be sent to the OpenAI TTS API with its specific voice and speed.
        *   If `multi_voice_data` is not available, or if a user has selected a specific voice preset, a fallback single-voice logic is used. The text (potentially including the title) is chunked into manageable pieces.
        *   Each chunk or segment is then sent to the OpenAI TTS API, which returns an audio segment.
    *   **Audio Stitching**: The individual audio segments generated by the TTS API are concatenated in the correct order to form a single, complete audio file for the article.

6.  **Finalization**:
    *   The complete audio file is saved to a designated media storage location.
    *   A de-essing filter is applied during export to reduce harsh sibilance.
    *   The path to this audio file is stored in `article.audio_file_path`.
    *   The `article.status` is updated to `COMPLETED`.
    *   Other relevant fields, including `article.summary`, `article.multi_voice_data`, and `article.voice_parameters` (if applicable), are saved to the database.

7.  **Error Handling**:
    *   If any unrecoverable error occurs during the processing steps, the `article.status` is set to `FAILED`.
    *   A description of the error is saved in `article.error_message` for debugging and user information.
    *   The system includes retry mechanisms for transient errors.

## 3. RSS Feed Generation (`UserFeed` in `feeds.py`)

Once articles are successfully processed, they become available in the user's personalized RSS feed.

*   The system generates a unique RSS feed for each user (e.g., `UserFeed`).
*   When a user's RSS feed is requested, the system queries for `Article` objects belonging to that user that have a `status` of `COMPLETED`.
*   For each completed article, an RSS feed item (`<item>`) is generated. The `item_description` for each item is particularly important and includes:
    *   A link to the original source article (`article.source_url`), if one was provided.
    *   The **generated summary** (`article.summary`) of the article, providing a quick overview of its content.
    *   The MP3 audio file as an enclosure (`<enclosure>`), allowing podcast clients to download and play the generated audio.

## 4. Overall Flow

The entire pipeline relies on several key components:

*   **Django Models**:
    *   `Article`: Stores the text content, metadata, status, summary, and paths to generated audio.
    *   `Feed`: Manages user subscriptions to external RSS feeds and user-specific settings.
*   **Celery Tasks**:
    *   `process_article`: Handles the computationally intensive article processing in the background, ensuring the web application remains responsive.
    *   Other tasks manage fetching from followed feeds and system maintenance (e.g., `check_stale_articles`).
*   **Services**:
    *   `ContentAnalysisService`: Responsible for LLM-based content analysis, summary generation, and voice segmentation.
    *   `VoiceConfigurationService`: Manages how voice preferences are applied to articles.
    *   `ChunkToneService` / `VoiceParameterGenerationService`: More advanced services for nuanced voice control and tone.
    *   OpenAI API client interactions for TTS and LLM functionalities.

This architecture allows for scalable and robust processing of articles into audio format, delivered conveniently to users via RSS feeds.
